# HelpDesk 360

HelpDesk 360 is a local IT support tracker with a React frontend, an Express JSON API, and a persistent SQLite database. The API enforces employee and technician permissions; ticket rows, assignments, status history, comments, notifications, and ratings are stored in SQL.

## Requirements

- Node.js 20 and npm (the setup and run scripts select Node 20 through npm if the system default differs)
- Docker Compose (optional)

## How to run it

From a fresh clone, open a terminal in the repository root:

```sh
cp .env.example .env
npm run setup && npm run dev
```

On Windows PowerShell, copy the file with `Copy-Item .env.example .env`, then run `npm run setup; if ($LASTEXITCODE -eq 0) { npm run dev }`. The app opens at <http://localhost:5173>; the API listens on <http://localhost:4000>. The first backend start creates `data/helpdesk.sqlite`, the schema, demo accounts, and 24 demo tickets. The SQLite file remains on disk across backend restarts.

To run the production-style container setup, copy `.env.example` to `.env`, then run:

```sh
docker compose up --build
```

Open <http://localhost:3000>. Compose stores the SQLite database in the named `helpdesk_data` volume. Stop with `Ctrl+C`; use `docker compose down` to stop containers while keeping data. `docker compose down -v` also deletes the demo database.

For a frontend production build, run `npm run build`. Run automated backend integration tests with `npm test`; run the backend restart and persistence smoke check with `npm run verify`.

## Data and access rules

- Employees can create tickets, read their own tickets, reply to the IT team, and rate resolved work. Technicians can add internal notes; employee detail responses omit those rows.
- Technicians can read the full queue, claim an unassigned active ticket from its detail page, reassign work, and advance status one step at a time: open → in-progress → resolved → closed. Claiming assigns the ticket without changing its status.
- Ticket timestamps are set server-side in UTC. Dashboard counts and charts are calculated by SQL queries; the dashboard includes a plain-language explanation for each measure.
- Login uses a bcrypt password hash and an httpOnly, SameSite=Lax cookie. API errors return JSON with an `error` field. Ticket text is stored as plain text and React renders it as escaped text.
- `.env` is ignored by git. Replace `JWT_SECRET` with a private value before production use; the server refuses to start in production when it is missing or the sample placeholder.

## API overview

All routes are under `/api`. Login and logout are `POST /auth/login` and `POST /auth/logout`; `GET /auth/me` reads the current session. `GET /me/stats` returns SQL-backed menu totals for the current user. Ticket routes include `POST /tickets`, `GET /tickets`, `GET /tickets/:id`, technician-only `POST /tickets/:id/claim` and `PATCH /tickets/:id`, reporter-only `POST /tickets/:id/rating`, and `POST /tickets/:id/comments`. A technician may send comments as `reply` or `internal_note`; employee replies use `reply`. A `resolution_note` on `PATCH` with `status: "resolved"` is optional to the API and is stored as a `resolution` comment in the same transaction.

Technician `GET /tickets` filters are URL-synced: `status` accepts one value or a comma-separated list, `active=1`, `overdue=1`, `assigned=unassigned|me|<username or user ID>`, `priority`, and `category` are supported. Queue saved views and dashboard drill-downs use the same SQL filter builder. Technicians can query `GET /users?role=technician` and `GET /dashboard`. `GET /notifications` lists newest first; `POST /notifications/read` accepts `{ "ids": [...] }` or `{ "all": true }`. `GET /health` is a public health check, polled by the app every 30 seconds.

List items keep the handout contract fields: `id`, `title`, `category`, `priority`, `status`, `reported_by`, `assigned_to`, `created_at`, and `updated_at`. `client_token` is an optional UUID idempotency key; submitting it again returns the original row.

## Manual acceptance checklist

1. Sign in as `priya.nair`, submit a ticket, and open My tickets.
2. Sign out and sign in as `arjun.mehta`; open the unassigned ticket in Queue and confirm it is claimed without a status change.
3. Reassign if needed, then advance its status to In progress.
4. Sign back in as `priya.nair`; confirm the technician and updated status are shown.
5. Restart the backend and refresh the browser; confirm the ticket and updates remain.
6. Open Dashboard as a technician and compare a displayed count to the `tickets` table in `data/helpdesk.sqlite`.

Automated restart/persistence verification is also available through `bash scripts/verify.sh`. The benchmark helper `node scripts/bench.js` requires a running API and uses the demo technician credentials from `.env` variables or its documented defaults.
